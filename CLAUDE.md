# CLAUDE.md

open-mtp-client: a native macOS app (Rust, iced UI) for moving files between a Mac and an Android phone over MTP.
The product is called open-mtp-client everywhere the user sees it.
It was called mtprust until 2026-10-16; settings are moved from `Application Support/mtprust/` on first launch.
The feature table in README.md says what is done and what is planned; CONTRIBUTING.md says how to work on it.

## Commands

- `make run` runs against a real USB device, as an optimized build: a debug build of the UI is many times slower and made big folders painful. `make run PROFILE=` builds debug (faster to compile). Judge performance only on a release build.
- `make run-virtual` runs against a fake phone backed by `.virtual-phone/` (no hardware needed). `make run-virtual-two` plugs in two (`.virtual-phone/` and `.virtual-phone-2/`; `OPEN_MTP_CLIENT_VIRTUAL_DIR` takes folders joined with `:`, each a phone).
- `make app` builds `dist/open-mtp-client.app` for **both kinds of Mac**, with the command-line tool inside (`Contents/MacOS/open-mtp-client-cli`, joined and checked like the app, signed before the bundle since nested code must be, and run with `--help` as a build step; Help's About shows its path and a shell-quoted `ln -sf … /usr/local/bin/open-mtp-client-cli` line to copy, only when `wire::bundled_cli_beside` finds it beside the app's program in `<name>.app/Contents/MacOS`): `make universal` builds release binaries of both for `aarch64-apple-darwin` and `x86_64-apple-darwin` (each with `MACOSX_DEPLOYMENT_TARGET` read from `Info.plist`'s `LSMinimumSystemVersion`, so they can't disagree), joins them with `lipo` and checks each slice (`-verify_arch` takes one architecture per call); the bundle is then signed ad hoc (`codesign --sign -`: Apple Silicon runs no unsigned code, and joining loses the linker's signatures) and verified. Icns from `assets/icon-1024.png`, `packaging/Info.plist` with `@VERSION@` filled in. `the_app_is_built_once_for_both_kinds_of_mac` guards the Makefile. `make test-intel` runs the whole suite as Intel code (under Rosetta on Apple Silicon). The diagnostics report says "under Rosetta" when the app runs translated (`Processes::translated`, `sysctl.proc_translated`). `make icon` redraws the icon from `scripts/make_icon.py`.
- `make cli` builds `target/release/open-mtp-client-cli` (`cmd/open-mtp-client-cli`: `phones`, `storages`, `info`, `ls`, `pull <path>...`, `push`, `mkdir [-p]`, `rm` and `mv` on the phone, with `--virtual <folder>`, `--phone`, `--storage`, `--hidden`, `--skip|--replace|--replace-older|--keep-both`, `--move` (pull: the app's checked move; push: originals to the Trash), `-p` (mkdir, push: folders on the way), `-y/--yes` (rm), `--json`): the app's own services with no window, so a copy is checked, resumed and quarantined as from the app; `push` asks the phone what is taken first and replaces nothing unless told; several paths go one request per phone folder (`by_folder`); `mv` is the explorer's paste, through the Mac when the phone can't (`Unsupported`). `run` takes a `World` (`ask`: the yes/no prompt, `None` when stdin isn't a terminal, so `rm` without `--yes` refuses in a script; `terminal`: progress on stderr as a bar redrawn in place, else a line per whole percent and when the last file is done (`Progress`); `cancel`: flipped by ctrl-c in `main.rs` (tokio's `signal` feature, the CLI only), so a copy stops at its next safe point; `trash`: `local::system_trash` in the program, a recorder in tests, never the real one). Exit codes follow sysexits.h (`cli::exit_code`: 64 usage, 66 not found, 69 no phone, 73 can't create, 75 try again, 130 stopped with ctrl-c, 1 some files failed). Its parser and commands are `cli.rs`, tested against the virtual phone, and `tests/binary.rs` runs the built program (`rm` in a script refuses).
- `make test-large` runs the two tests that move a whole 4.7 GB file each way (seconds on a release build, 4.7 GB written at each end, so they are `#[ignore]`d from `make test`).
- `make test`, `make lint` (clippy with warnings as errors) and `make coverage` (fails under 75% line coverage) must pass before a commit.
- `make prune` runs first in every target that compiles debug code (`run*`, `build`, `test`, `lint`, `coverage`): cargo never prunes `target/` (one checkout reached 201 GB), so past `TARGET_MAX_GB` (12; `make test TARGET_MAX_GB=1000` turns it off) it removes the debug profile and `target/llvm-cov-target`, never release or universal builds, and the next compile is one full debug build (~30 s). The 200 GB itself was `.o` files macOS leaves beside debug binaries (`split-debuginfo = "unpacked"`, measured 1,501 new ones a rebuild), which `[profile.dev] split-debuginfo = "off"` stops; incremental caches (~2 GB) are kept because turning them off made rebuilds 4-5 times slower (3 s to 14 s). `a_target_folder_past_its_size_loses_the_debug_and_coverage_builds_only` runs the real recipe with a fake `cargo`.

## Tests

Every behaviour ships with its test in the same commit — service rules, retry/recovery paths, handler
state transitions, app routing and `wire.rs` bindings, not only pure mappers. Seams for the hard parts:
- Device behaviour: `mtp-rs` virtual device via `service::testing::virtual_source` (unique serial per test).
  Android quirks have hooks, e.g. `mtp_rs::rekey_virtual_object` for stale handles.
- Handlers: fakes in `handler/testing.rs`; async work lives in free `async fn`s (`load_connection`,
  `fetch`) so it is testable without running an iced `Task`; call `view()` in each state.
- Only `main.rs` is expected to stay uncovered.
- Driving the real app: send keys only after checking the app is frontmost too (the user may be working). If a guard aborts, stop the live check rather than retrying — each launch steals focus from the user.
- Driving the real app with System Events: `keystroke "1"` sends the numeric keypad's 1 (`Code::Numpad1`), not the main row's (`Digit1`), so a digit shortcut must be sent as `key code 18` (1), 19 (2), …; letters are fine as `keystroke`.
- Driving the real app: launch with `HOME=<scratch dir>` so the Mac pane never points at real files, and click only through a guard that checks the app is frontmost and uses window-relative positions — a fixed-position click once landed in another app.

## Performance (a standing rule)

The app has to stay fast however much a phone holds; a camera folder has thousands of files.
- Nothing the UI does per redraw may grow with the number of files: build only what is on screen (`handler/explorer/window.rs`), never a widget per file. `view_cost_does_not_grow_with_the_folder` and the `rows_built` tests guard this.
- Never block the UI thread. Phone work is async, and anything long streams its progress.
- Count phone round trips: each is a real USB request, ~5 ms on a real phone. Don't put a whole-folder listing on an edit or refresh path.
- Cap every cache (thumbnails are capped at 400) and keep memory flat while scrolling.
- Check each new feature against 5,000+ entries, judge speed on a release build (`make run`), and note measured numbers in the pull request when a change touches performance.

## Layout (Go-style, mapped onto Cargo)

```
cmd/open-mtp-client-cli/             the command-line tool (binary crate, `cli.rs`)
cmd/open-mtp-client/                 the iced desktop app (binary crate)
  main.rs                    builds the iced application
  wire.rs                    hand-written composition root; also binds internal services to handler traits
  app.rs                     root UI: routes messages to handlers, lays out their views
  handler/{domain}/
    handler.rs               Message enum, update/view; declares the `Service` trait it needs
    request.rs               user intents (`Request` enum)
    response.rs              display-ready view models (strings already formatted)
    mapper.rs                request → dto, dto → response
  handler/error.rs           shared error copy (dto::Error → title + hint) for every handler
  handler/format.rs          shared formatting (bytes, timestamps)
internal/                    library crate `internal`
  dto/                       business entities and errors: plain structs, no serde, no UI types
  service/{domain}/
    service.rs               domain logic and business rules; tests live here
    mapper.rs                client (mtp-rs) types → dto
  service/mapper.rs          client errors → dto::Error, shared by every domain
```

Rules:
- Handlers never import `mtp_rs`; services never import `iced`. Only `dto` crosses the boundary.
- A handler's `Service` trait uses `#[async_trait]`; its implementation for the concrete service goes in `wire.rs`.
- No `wire_gen.rs`: there is no DI codegen in Rust, `wire.rs` is the whole graph.
- Services that need the device session take `Arc<device::Service>` and use its `session()` / `handle_error()`.
- `handler/explorer` is the generic file pane (`Volume::phone_tools` marks the phone pane, whose toolbar offers Search and Mirror…). `app.rs` runs two of them over an `explorer::Volume`: the device pane (MTP storage id, bound to `service::explorer`) and the Mac pane (volume 0, bound to `service::local`). Pane features go in the explorer handler once and work on both sides.
- Keyboard: `keymap.rs` maps (key, physical key, modifiers) to a `Shortcut`; letters use the physical `Code` so non-Latin layouts work. `app.rs` subscribes to `keyboard::listen()` (only keys no widget captured), routes shortcuts to the active pane, and owns the ⌘C/⌘X/⌘V clipboard (`Clipboard { side, selections, cut }`: a ⌘X cut is made on either pane and dimmed in the pane it came from by `explorer::Handler::set_cut` (`App::set_clipboard` tells both), and is used up only by a paste that went through, so a refused paste can be retried; a Mac cut pasted on the phone is a move to the phone (below) and waits, still cut, while no phone folder is open; a cut pasted on the Mac is a move that removes each original from the phone once its copy is checked: `transfer::Service::download_as(Paste::Move, …)`). Selection state is the pure `handler/explorer/selection.rs`.
- Finder drops arrive as window events, one per file, with no cursor position (`iced::event::listen_with(file_drop)`); `app.rs` batches them for `DROP_SETTLE` and uploads into the phone pane. Timers inside `Task::perform` must be created inside the `async` block — creating `tokio::time::sleep` eagerly panics outside the runtime (a test caught it).
- Settings: `dto::Settings` (no serde) ↔ `service/settings/mapper.rs` `SettingsFile` (serde, `#[serde(default)]`, versioned). `app.rs` owns applying them (`apply_settings`) and intercepts the panes' footer toggles so there is one source of truth.
- Import (`transfer/import.rs`, `handler/import`, sidebar "Import new photos…"): the selected storage's `/DCIM` only (`Pictures/Screenshots` is deliberately out), walked with `explorer::Service::walk_from` (the search's `Walk` started at a path; a re-key restart re-resolves that path; `next_raw` yields the phone's own `ObjectInfo`) with hidden always off, photos and videos only (`FileKind`). Files are flattened into the Mac pane's folder, or into folders by the date `explorer::shown_date` gives (the date the pane shows; undated files go in the root): `dto::ImportFolders` None, Day ("2026-03-14"), Month ("2026-03") or YearMonth ("2026/03"), named by the pure `folder_for`, with Finder's keep-both for a taken name (`resolve_file`'s `claimed` set covers names taken within the same plan). The steps run through `run_steps` (`Run`, `Executed`), the copy loop every download shares. New means: not at its target with the same size and date, and not in the `ImportRecord` (one `.tsv` per phone serial in `Application Support/open-mtp-client/imported`, written temp-then-rename; only `Outcome::Verified` copies go in, each line `record_key` (path, size, date) plus, since 106, a fourth field: where the copy went (`ImportRecord::targets`; a path with a tab or line break keeps its key only, and lines without one are read as before); a phone without a serial gets none; a failed write costs nothing; deleting the folder resets it). The record is what keeps a photo moved or deleted on the Mac from coming back, and what makes switching between layouts safe. A cancelled or failed import records nothing (no outcomes come back on that path), so its arrivals are found by `resolve_file` next time only if the layout is unchanged. The dialog previews first (`import_preview`, streamed counts, own `Cancel` and preview id like the search), enables Import only when something is new, and `app.rs` queues `Job::Import` (phone work, retryable as the same request). The choice is `Settings::import_folders` (file key `importFolders`, by name; a file from before it with `importByDate: true` reads as Day, and both keys are written so an older build still reads a day; a saved import job keeps `folders` beside `byDate` the same way). **Freeing the phone** (`ImportRequest::remove_from_phone`, the dialog's "Remove them from the phone once imported", `Settings::import_remove`, file key `importRemove`, off by default, app.rs saves it as for the folders): the copy runs with `moving: true` (forced to disk, as a move's), then `remove_imported` removes, one file at a time through the move's `remove_one` (looked up again: same name, size and date), only steps whose outcome is `Verified` (an `AlreadyThere` file counts: its copy is on the Mac), each with its `Origin` from the plan (`Planned::originals`, none for the Mac's day folders), **never a folder**; `Unchecked` stays with its reason; a cancel or lost phone leaves the rest, a cancelled or failed import removes nothing. `Removal::freed` adds up the bytes; the summary says "3 files removed from the phone, 12 B freed" and an import is never called a move (`to_import_summary` maps it without the removal). `note_removed` keeps the folder memory true. The phone pane stays visible under the dialog, so its thumbnails share the session with the preview's walk.
- Free Up Space ("Free Up Space…" under the open phone in the sidebar, `device::Request::FreeUpSpace`, which `App::open_space` turns into the dialog `handler/space` (imported in `app.rs` as `freeing`, since `space` is iced's widget there), a dialog like Import for every gate: `dialog_is_open`, the view chain, Escape, `close_device_pane`, and `why_not_switch` while it looks or removes (`is_busy`)): `transfer::Service::space_report` (`transfer/space.rs`, tests in `transfer/spacing.rs`) walks the storage once with the search's `walk_from("/", hidden off)` and keeps what it saw (`SpaceScan`: storage, epoch, each file's `ObjectInfo` by path) for removing. **Copies** (`duplicates`): by size (empty files and MTP's "4 GB or more" left out; one pass), then, where the phone reads from an offset, by a SHA-256 of the first and last `ENDS` (64 KB) through `read_range` (a file the phone won't read can't be called a copy), then by a SHA-256 of the whole file read with `download_windowed` (nothing written; cancel between windows; a phone without ranged reads is read whole, cancelled with `download.cancel`; a file that comes short of its size is no copy); a group exists only when every byte agrees. The one to keep comes first (`original_first`: the oldest, then under `DCIM/Camera`, then by path); groups by bytes to gain. **Already imported**: a DCIM file whose `ImportRecord::targets` entry is still a real file at the phone's size and date (`is_same_file`), so a copy moved away on the Mac is never offered and only imports from now on count. **The biggest files** are 74's search, opened by "Biggest Files…" with `SortBy(Size)`. `free_up(FreeUpRequest)` removes only paths the scan of this storage on this connection holds, each through the move's `remove_one` (same name, size and date, never a folder), cancel or a lost phone between files, `note_removed` after; a path not in the scan stays (`Why::Changed`). The dialog builds its list once per look (`mapper::lines`, fixed-height `Line`s, windowed with `explorer::window::rows`, `ROW`/`LIST_HEIGHT`), picks by path (`HashSet`), "Select Copies" leaves each group's first, a file in both lists counts once in the bytes, asks before removing ("… will be deleted from the phone for good"), and after a removal `app.rs` reloads the storages and the phone pane. 5,000 files with 500 pairs: 0.73 s on the virtual phone, release.
- Mirror (`transfer/compare.rs`, `transfer/mirror.rs`, `handler/mirror`, "Mirror…" in the phone pane's toolbar): the contents of the folder the phone pane shows and the one the Mac pane shows, either way. `compare` is pure and shared by both directions: paths relative to each folder, matched ignoring case (APFS); two items on one side differing only in case, or a file where a folder is, are a `Conflict` that stops its whole branch; hidden items (any dot component, which covers the app's own part and scratch files and `.DS_Store`) are invisible on both sides; extras are reported once per branch and removed only with `remove_extras`; `is_same` is size (unknown on either side forgives) and date ±2 s. The phone side is always read for real (`Walk::fresh`): a file changed in place keeps its folder's item count, so the index would hide it; the run reuses a preview's reading (`mirror_reading`) of the same folder, on the same connection, for 2 minutes. A truncated walk is an error (what it missed would look like extras). Onto the Mac: new files go straight to their place; changed ones are copied into `.open-mtp-client-mirror` and swapped in only when `Verified` (the old one moved aside first, put back if the swap fails; a link where the old file is is not written through); old versions and removed extras gather in one `.open-mtp-client-replaced-<ms>` folder that goes to the Trash in one call; without a Trash a mirror that would replace or remove is `Unsupported` before anything is copied; a name on the Mac where a folder should go that is not a real folder (a link to a folder elsewhere) is a conflict, so nothing is written outside the Mac folder. Onto the phone: new folders go over whole with only what was planned inside (`only_planned`, so hidden files stay), a changed file is deleted then sent (`replaced` counts only what went over: a failure about one file is kept by the `Sender`, not returned), extras are deleted for good; then `forget_listings_below`. The dialog does not offer removing extras on the Mac for the home folder or `/`. `resolve_file` treats a path that can't exist (a file where a folder on the way should be) as free, rather than numbering for ever. **Saved mirrors** (`dto::SavedMirror`: the phone as a `PinPhone`, both folders, direction, remove extras; `MOST_MIRRORS` = 20) are kept in `places.json` beside the pins (`places::Service::mirrors`/`save_mirrors`; each save rewrites the file keeping the other list, `to_mirrors` trusts nothing a hand-edited file says): "Save This Mirror" in the dialog (only with a serial, `mirror::Handler::offer_saving`; `app.rs` keeps `to_save()` through `places::Handler::save_mirror`, which replaces the same mirror (`same_mirror`: same phone, storage, folders, direction) to take a new choice of what it removes) and "Saved in the sidebar" once `places::Handler::is_saved` says so (`App::sync_mirror_saved` after every mirror message). The sidebar's "Mirrors" lists the open phone's on storages it has now (`mapper::storage_of`, `mapper::mirror_label` "Camera → Phone photos"); a click (`places::Message::OpenMirror { at, storage_id }`, not over a dialog) opens the dialog as saved (`open_saved`), which compares first; **nothing runs until Mirror is clicked**, never at connect.
- Quick Look (Space, `handler/preview`): Mac files go straight to `local::QuickLook` (`SystemQuickLook` runs `qlmanage -p`, one at a time, killed when Space is pressed again while it is open (the panel takes the focus, so the app must be in front again) or when the app drops it on a normal quit (a panel can outlive a killed app); tests use `RecordingQuickLook`, never the real one). Phone files are fetched first by `transfer::Service::fetch_for_preview` (`transfer/preview.rs`): the phone's name must be one plain name before anything is joined to it (it is untrusted, and a stale copy of that name is removed before the download's own check), at most `PREVIEW_MOST` (20), no folders, nothing over `PREVIEW_LARGEST` (1 GB) or of a size the phone doesn't give, the second of two names differing only in case left out; it is `download_as(Copy)` into a cache under `$TMPDIR/open-mtp-client/preview/<hex serial>-<storage>/<hash of the folder>` (`0700`, emptied at startup by `wire::fresh_preview_cache`, pruned to `PREVIEW_CACHE` (2 GB) by the folder used longest ago, never the one being looked in); a copy that differs from the phone's file is removed first so the look is at its own name, and a second look copies nothing. The fetch runs outside the queue, beside the pane, so it is phone work for `why_not_switch`, `close_device_pane` cancels it, and Escape stops it before anything else, and each fetch has an id so a stopped one's late answer is dropped; besides thumbnails it is the only thing that shares the phone's session outside the queue. Its banner is below the panes. Opening a file in its Mac app (double-click, ↵, the menu's Open on a single item; `explorer::Message::OpenFile`, which `app.rs` routes) is the same fetch followed by `local::Opener` (`SystemOpener` runs `open -- <path>`, reaped off the UI thread; `RecordingOpener` in tests); Mac files go straight to it. **Share…** (right-click on items, File menu; `explorer::MenuAction::Share`, `menubar::Command::Share`, `App::share`) is the same again: Mac files straight to `local::Sharer` (`SystemSharer` shows AppKit's `NSSharingServicePicker` from the key window's content view, pointing at the right-click (`explorer::Handler::menu_at`, read before the menu closes; the File menu has none, so the window's middle), `share::anchor` turning top-left points into AppKit's bottom-left unless the view is flipped, the picker kept in a thread-local while it shows; off the main thread it shows nothing and says so; `RecordingSharer` in tests), phone files after `fetch_for_preview` (`preview::Then::Share(at)`, the banner says "to share", the same limits and refusals); `local::share_files` says a file gone since it was listed is gone rather than offering nothing. Every fetched copy is marked `com.apple.quarantine` (`0083;<hex time>;open-mtp-client;`, as a browser marks a download, with `xattr -w`) so the Mac checks it before running anything a phone could hold (`.command`, installers), and made `0444` so an app says it is locked: edits never reach the phone, and the cache is emptied at the next launch.
- Editing a phone file on the Mac ("Edit on Mac" in the phone pane's item menu, `explorer::MenuAction::EditOnMac`, app-wide, offered only on the phone (`menu::Context::edit_on_mac`), enabled for one file (`explorer::Handler::single_file`, one `by_name` lookup since the menu state asks after every message); File › Edit on Mac, `menubar::Command::EditOnMac`, `State::can_edit`): `App::edit_on_mac` sends a `dto::EditRequest` (phone key, storage, folder, name) to `transfer::Handler::edit`. `transfer::Service::edit_on_mac` (`transfer/editing.rs`, tests in `transfer/edited.rs`) checks as Quick Look's fetch does (one plain name, a file, a size the phone gives, at most `PREVIEW_LARGEST`; else `Error::NotEditable`; at most `MOST_EDITS` (20), else `Error::TooManyEdits`), and downloads it into its own `0700` folder (named by a hash of phone, storage, folder and name) under `Application Support/open-mtp-client/editing` (`wire::editing_dir`, not a cache), writable (not `0444` as previews are), with `manifest.json` (temp-then-rename: where it came from, the copy's `CopyState` when fetched, the phone's size and date as fetched). A file already being edited is not fetched again. `wire::Transfers::with_editing(dir, opener)` turns it on and opens the copy with `local::open_in_app` (a recorder in tests, never the real `open`). `working_copies` reads the manifests (at start-up, `transfer::Handler::load_edits`; a manifest naming anything but one plain name, or whose copy has gone, is left out). While there are copies `App` subscribes to `transfer::EDIT_CHECK` (2 s) → `Message::CheckEdits` → `copy_states` (stat off the UI thread); an `Edit` is `saved` when its copy differs from what was fetched and was the same at the last look (an app writing it isn't caught half way); a copy gone from the Mac drops its row. Rows in the transfer panel: "notes.txt is open for editing on the Mac" with Stop Editing, then "notes.txt was changed on the Mac" with Discard and Send to Phone (only while its own phone is open: `set_open_phone`, synced after every update from `device::Handler::open_key`; else "Connect the phone it came from to send it"). Send queues `Job::SendEdit` (once; phone work; `resumed()` itself, so a lost phone holds it as 93 does; never in the saved queue: `to_saved` returns `None`, the manifest is what is kept), which runs `send_edit`: first the phone open now must be the copy's own (`device::Service::open_key`), else `Error::OtherPhone` before anything is asked or sent (not a lost-phone error, which would close the phone that is open); `forget_phone` drops waiting Sends, their copies kept; then `open_folder_confirmed` asks about that one file; still the size and date fetched → upload with `Conflict::Replace` (deleted, then sent; the phone keeps no old version), else `KeepBoth` (beside it as "notes (1).txt"); the copy's folder goes once the upload has no failures, and its row with it (`mapper::to_edit_summary`: "Sent “notes.txt” back to the phone" or "Sent your edit as “notes (1).txt”"). `discard_edit` removes the folder; `copy_place` refuses a copy whose id or path points anywhere but its own folder.
- Get Info (⌘I, menu "Get Info" on an item or on empty space: `MenuAction::GetInfo`/`GetInfoHere`, app-wide; `handler/info`): `Subject { place, folder, items }` from `explorer::Handler::info_subject()` (the selected `dto::Entry`s, none = the folder itself; the phone `storage_id` is the pane's own `volume_id`, the device panel only names it). The pure `mapper::base` adds the selected files and the selected folders themselves; `folders_to_count` lists what is walked; each `open` bumps a run id and has its own `dto::Cancel` (a stopped count's word is dropped). The phone count is `explorer::Service::tally` over `walk_from(.., include_hidden: true, ..)`, so it is bounded, stops between pieces and reuses the folder memory (a just-listed 5,000-file folder costs ≤ 1 full read); the Mac count is `local::Service::tally` in `spawn_blocking`, `DirEntry::file_type` so a link is counted, never followed, and a folder macOS keeps private is `Tally::unreadable`, not an error. Hidden items are counted (the dialog says so). **What fills it**: `Tally::by_kind` holds the known bytes per `dto::SpaceKind` (Photos, Videos, Music, Documents, Archives, Apps (.apk/.apks/.xapk, as the badges), Other), filled by `Tally::add_file(name, size)`, the one place a file is counted (the phone's walk, the Mac's walk and `mapper::base`; an unknown size is in no kind); `mapper::kind_shares` (two or more files with known bytes) gives "Videos 41.2 GB" with its part of the bar in thousandths (at least 1), most first, and the dialog draws a split bar and the kinds under it (`kinds_view`, `kind_colour`); a click on a kind with a `FileKind` sends `info::Request::ShowKind`, which `app.rs` turns into the phone's search for that kind ordered by size, or the Mac pane's kind filter, and the dialog closes. No request more than the count makes. It is a dialog like Settings and Help: the three gating sites in `app.rs` (the `view` chain, the one-dialog-at-a-time closes, `run`'s Escape/⌘I) include it, and `close_device_pane` closes it when it is about the phone. The status bar's "3 of 9 selected · 12.4 MB" uses `by_name` (built in `resort`), one lookup per selected name; a folder's own size is never added (`selected_size`); `filtered_status` is unchanged. After a transfer `TransferSummary::arrival` (`dto::Arrival`) counts what was meant to arrive against what is there: downloads and imports from the plan and outcomes (`service::arrival`; `Verified` = checked), uploads from the planned nodes, `files_done` and `already_there`, `checked` only when files were read back (`Options::verify`: moves); `complete` is false when the plan skipped a folder that loops (`plan.unwalked`); mirrors and copies through the Mac have none. The panel says "all arrived" only when every file was checked, "all sent, and the phone took each one" for a plain upload.
- A transfer's report (`dto::FileReport` in `TransferSummary::report`, at most `REPORT_MOST` = 100,000, the rest counted in `report_left_out`): downloads, moves to the Mac and imports build it from what they already hold, `service::report(plan, outcomes, failures, fates)` (one entry per file step, in the order copied: `FileOutcome` Copied/Resumed with `checked` = `Verified`, AlreadyThere, Replaced (only a `Verified` staged copy is swapped in; an unchecked one is NotCopied), Failed with its `FileFailure`, NotCopied; `from` is the phone's own path when the Mac name differs; then `Plan::skipped`, the labels the taken-names answer left alone). - Crashes (`service/crash`, `handler/crash`, `wire::watch_for_crashes`, `wire::CrashDesk`): `main` installs a panic hook before anything else (`Crashes::install`, which also calls the previous hook, so stderr still gets the panic). ## MTP and macOS gotchas

- The MTP client is `mtp-rs` (pure Rust over `nusb`, no libusb). Its `virtual-device` feature is enabled in normal builds for `make run-virtual`. It is **vendored** (`vendor/mtp-rs`, 0.34.0 plus `vendor/mtp-rs.patch`, via `[patch.crates-io]`; outside the workspace): the patch adds `MtpDevice::battery_level()`, `is_android()` and `supports_operation(code)` and their virtual-device support (`VirtualPhone::battery`, `mtp_rs::set_virtual_battery_level`). the patch also hardens it against bad replies (`vendor/README.md`: a response shorter than its header, a buffered reply of any size, endless empty packets, a lone surrogate in a name), tested by `make test-vendor`, which `make test` does not run. Change the vendored crate only through that patch (regenerate it with `diff -ruN` against `~/.cargo/registry/src/*/mtp-rs-0.34.0`) and say so in its files; `vendor/README.md` has the upgrade recipe. Phones are opened with `use_object_prop_list(false)` (`device::service::builder`): 0.34 lists a folder by GetObjectPropList by default, which changes how every phone answers a listing, so a listing still goes a file at a time (as tried on real phones) until the other is tried on one. `vendor/mtp-rs/src/transport/virtual_device/CLAUDE.md` is the crate author's, not ours.
- Google's Android File Transfer agent grabs MTP devices on macOS; an exclusive-access error while it runs is mapped to `dto::Error::AndroidFileTransferRunning`.
- Android reports zero storages until the phone is unlocked and "File transfer" is chosen; the service turns that into `dto::Error::AllowStorageAccess`.
- Folders are addressed by path. Android re-keys object handles on a media rescan, so the explorer's path→handle cache is cleared and the path re-resolved once on `StaleHandle`/`NotFound`.
- Dates: Android writes zoneless phone-local times, shown as is; a date carrying a UTC offset is converted to the Mac's zone (`service/clock.rs`, chrono). The virtual device's clock is set to the Mac's zone so it behaves like a phone.
- Phone deletes that keep a copy in the Trash (Settings "Keep a copy of what I delete from the phone in the Trash", `Settings::keep_deleted`, file key `keepDeleted`, off by default, pushed to the phone pane by `apply_settings` → `explorer::Handler::set_keep_deleted`): the pane's delete question carries `Keep` (`Change::Delete { names, keep }`): `No` (setting off, or the Mac, which uses the Trash anyway), `Counting` (Delete greyed while `count_for_keeping` adds the files' known sizes by `by_name` and each folder's `Service::folder_size`, one at a time), then `Copy(bytes)` up to `dto::KEEP_MOST` (2 GB), `TooMuch(bytes)` over it, or `Unknown` (a "4 GB or more" file, a folder count that failed, was incomplete or had unreadable parts), worded by `mapper::delete_note`; a count for another question (`DeleteCounted { names }`) is dropped. Submitting `Copy` sends `Message::DeleteKeepingCopy(dto::DeleteRequest)` instead of deleting; `app.rs` queues `Job::DeleteKeeping` (phone work; no Pause and not kept across a quit: `resumed()` and `to_saved` are `None`), which runs `transfer::Service::delete_keeping_copy` (`transfer/deleting.rs`, tests in `transfer/deleted.rs`): refused without a Trash before anything; `download_run_onward_with(moving: true)` into a private `tempfile` scratch folder (checked, forced to disk, the room checked first as 62); a selected item whose every step is `Verified` goes to the Trash (one call, its top copy, `spawn_blocking`); one that isn't, or that the Trash refuses, has every outcome set to `NotCopied` and is `Kept` (`Why::NotCopied` or `Why::Refused`); then the move's `remove_originals` deletes from the phone only what was copied (looked up again, folders only once empty). A cancel or lost phone while copying deletes nothing. `mapper::to_delete_summary`: "Deleted 3 files from the phone", "copies are in the Mac's Trash", what stayed and why; the phone pane is read again (a removal from the phone already does that). Not Undo: putting back stays under Later.
- Edits: `service/names.rs` holds the name rules shared by both sides. Phone deletes are permanent (the pane confirms first); Mac deletes go through an injected `local::Trash` (real Trash in the app, a recorder in tests — never the user's Trash). The real one is `local::system_trash`: `NSFileManager`'s `trashItemAtURL` in this process (`trash_context`, `DeleteMethod::NsFileManager`), **never the crate's default**, which runs `osascript` to ask Finder with no time limit, needs leave to control Finder, and once left the Mac pane's delete on "Working…" for good; Finder's Put Back may be missing on some macOS versions. It blocks, so `local::Service` calls it only through `trash_off_thread` (`spawn_blocking`; the delete and a queued move to another disk), and the transfers through `spawn_blocking` too. `delete_object` is generic over the `Objects` trait so the empty-then-delete fallback is testable without a fussy device.
- The transfer handler is a queue: `current` (checking → asking → running), `waiting` (`VecDeque<Job>`), `history` (outcomes, retryable when failed). Every finish calls `start_next`. A finish with nothing running is ignored. **Pause** is a cancel the handler catches, with no change to the services (a transfer held in place would hold the phone's one session mid-window and trip the 90 s silence clock): `Request::Pause` cancels and marks the run `pausing`; a finish that is the cancel it asked for (`ErrorResponse::cancelled`) keeps `Job::resumed()` in `paused` (with the last progress, for the panel) instead of the history, and `start_next` waits while it is there; Resume puts it at the front of the queue; Cancel lists it as cancelled (retryable) and moves on; an `Ok` (too late) or another error finishes as usual. `resumed()` is the job that carries on without asking anything: downloads (their parts), imports and mirrors as they are, a move through the Mac merging, an upload whose names were free (or a move's Retry answer) with `Conflict::Merge`; none for copies inside one side, Mac pastes, or an upload answered Keep both or Skip (copy), and Pause isn't offered there. A paused job counts as phone work (`has_phone_work`), lets the Mac sleep and takes the Dock bar away; `forget_phone` ends a paused phone job. **A lost phone holds the job the same way** (`Paused::for_phone`): a finish that is `device_lost` (`Disconnected` or `Timeout`) while `Running` and not cancelling, for a job with `resumed()`, keeps that job in `paused` (`waits_for_phone`), the queue held behind it, its parts kept, notified when the window is behind (`mapper::phone_lost_note`); the panel says "Waiting for the phone: …" (`waiting_title`, `WAITING_NOTE`) with Cancel and no Resume (Resume is ignored); when the same phone opens again (`App`'s device route, after `forget_phone` has ended it for another phone) `phone_back` puts it at the front of the queue and starts it; a job without `resumed()`, or one lost while checking or asking, ends in the history as before. Tests that want a plain failure use `MacDiskFull`, not a lost phone.
- Uploads live in `service/transfer/upload.rs` (the domain's second file). The handler asks `existing()` before `upload()` so the conflict question comes before any byte; a failed or cancelled upload deletes the device's partial object (`UploadError::partial`). The question offers Skip, Keep both, Replace and, **for a copy only**, Replace older (`Conflict::ReplaceOlder`): a taken file is replaced only when the Mac's is newer by more than ±2 s (`upload::is_newer`; an unknown date on either side is not newer), folders merge and inside them the same rule holds (`Sender::only_newer`, `keep_theirs`), a file where a folder is (or the reverse) stays, and what stays is `skipped` and left out of the arrival's count. A move refuses it with `Unsupported` before anything is sent (`upload_as`), because a kept-back item's original would go to the Trash; it carries on after a pause and stands for a retry (`Job::resumed`, `Answer::for_a_retry`). The CLI's `--replace-older` is the same.
- Transfers (`service/transfer`): plan first (walk the selection for totals), deciding for each file `How`: `AlreadyThere` (same size and date, ±2 s), `Resume` (a hidden `.<name>.open-mtp-client-part` left by an earlier attempt) or `Fresh`; then copy through a part file renamed into place when complete. Cancel is a shared `dto::Cancel` checked between `download_windowed` windows and between files; a file that has fully arrived is placed rather than cancelled. When the phone stops or the user cancels, `settle_part` keeps the part (stamped with the phone's date: that is how a part is recognised as belonging to that file) only if the phone can read from an offset; a Mac-side failure, an empty part or an unknown date removes it. `tokio::fs::File` drops buffered writes: flush before judging how much a part holds. Folders merge, except through a symlink. Uploads skip files the phone already has (`same_file`). **Downloads ask about taken names** too: the run task first asks `transfer::Service::taken_on_mac` (a selected name holding a folder, or a different file; the very file is no question) and, only when something is taken, stops before a byte with `transfer::Message::CheckedOnMac`, so the panel asks ("… already exist on your Mac": Skip, Keep both, Replace older, Replace, for moves too, since what Replace older keeps back stays on the phone); nothing taken goes straight on in the same task, as before (`download_events`). The answer is kept in `Job::Download(request, mode, Answer)`; a resumed or retried download carries on with it (`Answer::Retried`). `download_with(mode, request, conflict, …)` plans with it (`plan_with`, `Walker::taken`): Keep both as before; Skip leaves a taken top item alone (a folder whole); Replace stages a different file under `.open-mtp-client-download` and, once `Verified`, swaps it in with Mirror's `swap_in` (the old one aside in one `.open-mtp-client-replaced-<ms>` folder that goes to the Trash in one call), and Replace older does so only for a phone file newer by more than ±2 s (`phone_is_newer`); folders merge; nothing of one kind replaces the other (skipped); a swap that fails is that file's failure and its step `NotCopied`, so a move keeps its original. Without a Trash, a download that would replace is `Unsupported` before anything is copied. `Plan::replaces`/`skipped` carry it; `download_as` is Keep both.
- Room before a byte moves (`transfer/room.rs`, tests in `transfer/roomy.rs`): `run_steps` (downloads, moves to the Mac, imports, mirrors onto the Mac, copies through the Mac) compares what is still to copy (`Step::bytes_to_copy`: already there costs nothing, a part file only its remainder) with the free space of the destination's volume (`Service::room`, `room::mac_room`: `statfs` of the nearest existing folder, named "on your Mac's disk" or "on “<volume>”"; `with_room` in tests) before the first byte, and refuses with `Error::NotEnoughRoom { needed, free, place }`; a copy through the Mac needs room for its biggest file on the Mac and for all of it on the phone (`Onward::room`, not for a retried move, whose plan overstates). Uploads and mirrors onto the phone compare with the storage's own free bytes (`storage.info()`, no extra request), less what a replaced item and a removed extra give back; a folder merged into is left out (its files are skipped as they are reached, so counting them would refuse a retry that fits). MTP's unknown free space (`u64::MAX`), or a disk that can't be asked, lets the transfer go ahead as before. The same `statfs` gives the volume's flags and file system (`room_of`): `Room::read_only` (`MNT_RDONLY`, defined here: libc has none for macOS) refuses before a byte with `Error::VolumeReadOnly(place)` (`ensure_writable`), and `Room::most_per_file` (`msdos`, FAT32: 4 GB less a byte) makes each file past it, or of MTP's "4 GB or more" (`room::too_big`), that file's failure, `Error::TooBigForVolume(place)`, left out of the room's count while the rest go (one such file alone is the whole download's error). `local::mapper::to_error` maps `ReadOnlyFilesystem`/`FileTooLarge` (EROFS, EFBIG) to the same errors, so the Mac pane's own copies say it too; the CLI exits 73 for both. `Room::free(free, place)` builds one with no other limit (tests, the phone). `VirtualPhone::capacity` sets the virtual storage's size, so a test can fill it.
- Batches carry on: `Failure::stops_the_batch` says which failures end a batch (connection, Mac disk full, cancel, planning limits) and which are about one file (`is_about_one_object`, plus any Mac error but disk full); the latter go in `TransferSummary::failures` and the loop moves on. If nothing was copied and every failure is the same, `whole_batch_failure` returns that error itself (an unwritable folder, a one-file copy) rather than a list. When a file fails, take its unsent bytes out of the totals (uploads track them in `Sender::unfinished`; do not read `file_bytes_done`, which can still hold the previous file's size).
- Remembered folders (`service/explorer/memory.rs`): the last full reading of recent folders is kept with the item count the phone reported and the connection epoch, and used only while both still match (`Service::open_folder`, `open_listing(allow_remembered)`). Never act on a remembered child without checking it with the phone: use `open_folder_confirmed(storage, path, names, must_exist)`, which asks about those files only and reads the folder for real if one is gone, changed or re-keyed. Anything that changes a phone folder keeps its memory true (`amend` after rename/delete/new folder) or forgets it (`forget_listings_below` after an upload). The pane passes `allow_remembered = false` for the Refresh button, phone change events and refreshes after a transfer; true for navigating, the refresh after an edit and toggling hidden files. Tests assert on `Service::full_reads()` (test-only), not on time: the virtual phone's slow call is the item count, the opposite of a real phone's. Asking a folder for a child by name goes through `Folder::child_named` and its `names::Index` (case-insensitive, built once): never search `children` for each of a selection's names, which is quadratic and built two strings per comparison.
- Copy and move inside the phone (`service/explorer/paste.rs`, `Service::paste`): the phone is never trusted to handle a name clash, because the virtual phone's `move_object` overwrites and a `copy_object` onto itself can empty the file, and a real phone is unknown. The `Pasting` trait is the seam (a recording fake drives the sequence tests; `pasting.rs` runs the same on the virtual phone). A copy with a free name is one `copy_object`; with a taken name it is made in a hidden scratch folder (`.open-mtp-client-paste-N`) in the target, renamed to the first free `name (n)`, moved out, and the scratch folder always removed. A move with a free name is one `move_object`; with a taken name the original is renamed *where it is* to a name free in both folders, then moved, and renamed back only when the phone answered no (`is_about_one_object`): after a timeout or reset the move may have happened with its reply lost, the item may already be in the target, and renaming it there to its old name would be the clash this code avoids. A phone that can't rename, move or make folders refuses the clash (`Refused::NameTaken`) instead of risking an overwrite. A folder into itself or below itself is `Error::IntoItself`, checked before anything is touched; capabilities come from `Capabilities`. Clash detection reads the target from the folder memory, valid while the item count matches, so a same-count swap on the phone can slip through (as for item 38). The app drops a phone clipboard whenever the phone pane closes for loss or disconnect (`App::close_device_pane`), since the next phone may share storage ids and paths. Every wait on the phone in edits and pastes is bounded (see "A silent phone"). A paste amends the remembered listings (target `added`, source `removed`), so showing the folders afterwards costs no per-file reads (`full_reads` pinned at 5,000 files). Per-object refusals are `PasteSummary::failures` and the rest go on (`failures::whole_batch_failure`, shared with transfers); a lost connection ends it. A phone that can't copy or move (`Capabilities`; most Android phones can't do one or both), or can but can't go round a name that is taken in the target (`can_paste_here`, decided by `batch_clashes` before anything is touched), answers `Error::Unsupported`, and the explorer handler turns that into `Message::PasteViaMac` (only when nothing was done yet); `app.rs` then queues a `Job::OnPhone` (`queue_through_mac`, a cut is used up once queued) that runs `transfer::Service::paste_through_mac` (see below). In the UI `explorer::Handler::paste(mode, selections)` runs one request per source folder in turn and reports them as one banner (`NoticeResponse`: `Copied as “a (1).jpg”`, `Copied 2 of 4 items`, failures named); edits wait while it runs; only a `Volume` with `pastes_within` can paste (both panes now; the default `Service::paste` of a fake says `Unsupported`).
- Moving phone → Mac (`transfer::Service::download_as(Paste::Move, …)`, `remove_originals`): copy, check, then remove. A step is `Verified` (all of it arrived, the phone gave a size, the file on the Mac is exactly that long, or it was already there with the phone's size and date), `Unchecked` (no size, or the size disagrees with what arrived: placed as a copy always was, original kept) or `NotCopied`. Android deletes a folder with everything in it, so never remove a folder for its contents: `remove_one` looks the object up again (same name, size and date, still a folder if it was one), deletes files one at a time, and deletes a folder only when the phone's own handle count says it is empty (`list_objects_stream(..).total()`, never the items that could be described: a file the phone lists but won't describe was never planned or copied) and nothing planned under it stayed (`should_remove`, `block`). `NotFound`/`StaleHandle` on an original mean it is not what was copied (`Why::Changed`). A refused or failed removal always leaves the original (`Removal::kept`/`left`); a lost phone or a cancel ends the removal, not the move, with the copies safe. `Plan::origins` is one `Origin` per step (the phone's own name and folder, not the Mac's numbered one). Removals tell the explorer through `note_removed`, so the pane's memory stays true. The result is `TransferSummary::removal`; a retry runs with `Removal::left` as its names, because the others are already gone. Mac → phone is below.
- Moving Mac → phone (`transfer/to_phone.rs`, `Service::upload_as(Paste::Move, …)`; ⌘X on the Mac pane, ⌘V on the phone): the upload runs with `Options { skip_identical: true, verify: true }` (every file read back from the phone; a file the phone already has with the same size and date counts as checked, which is what lets a retry finish), then each selected item's original goes to the Trash. **The Trash is where a mistake costs the user something, so an item goes only if** its upload was `confirmed` (the phone reported the size that was sent; no size, as some phones give for 4 GB or more, keeps it: `Why::Unchecked`; `upload::judge` is the pure verdict, because the virtual phone reports a 4.7 GB file's real size and so cannot produce the unknown case by itself), **and** `may_go` still finds it exactly as it was read before sending (`scan` again, compared by the pure `difference`: a changed size or date is `Why::Changed`; anything new in a folder is `Why::NotEmpty`), **and** nothing in it was left out (`LocalNode::left_out` counts what `scan` skips and is not Mac clutter: links to folders, sockets, pipes; the folder holding one stays, because the Trash would take it unseen). `.DS_Store` and `._*` go with their folder (uploads leave them out on purpose). A source the upload dropped altogether is `Why::NotCopied` and is *not* in `left` (a retry would drop it again). A `Conflict::Skip` item (`Delivered::skipped`) is neither trashed nor owed. An upload that ends in an error (cancel, lost phone) trashes nothing; a cancel during the Trash step stops and puts the rest in `left`. `Delivered` carries each item's scanned `LocalNode` (and its path) so items are matched by path, never by name or position. **A retry** (`Finished::retry_job`, for a move that got part way or failed outright) acts on what became of the question about taken names, which the job keeps (`Answer`): *nothing taken* (nothing was asked, so any folder of that name now is the first try's) retries without asking, with `Conflict::Merge`; the user's *Skip* or *Replace* still stands (a name skipped is still left alone, so a failed-outright retry must not put a numbered copy of it on the phone and its original in the Trash); *Keep both*, or a first try that never got as far as asking, asks again, because the folder the first try numbered is not known. `Merge` means: a folder merges into the one of the same name, a file that is there as it is (the very file or the numbered copy an earlier try made: `has_a_copy`, `Children::copy_of`) is left, and a different file or a file where a folder is goes in beside it under a numbered name (`Sender::keep_different`); nothing on the phone is replaced or deleted. `Conflict::Merge` is never offered to the user: it is what a retry means. One Trash call per selected item, not per file (the real one is slow on big folders), made with `spawn_blocking`. `Removal::from_mac` says the originals were on the Mac (through-Mac moves also have `direction: Upload`, so the side is never inferred); `Removal::left` then holds the source paths as given, which is what `Retry` sends again (`Job::Upload(request, mode)`); progress counts items (`TransferProgress::trashing`). The Trash is injected: `transfer::Service::new` has none and refuses a move with `Error::Unsupported` *before sending anything*; `wire::transfers(.., trash)` is the one place that picks it (`local::system_trash` in the app, a recorder that moves the item into a test's own folder in tests: **never call the real Trash from a test** — it fills the user's Trash). After a move the Mac pane is read again (`show_result`).
- Copy and move inside the Mac (`local/paste.rs`; ⌘C/⌘X then ⌘V in the Mac pane, or a drag onto a folder there): Finder-style, **nothing is ever replaced** (a taken name, ignoring case as APFS does, gets ` (1)`, `Taken` claims names once for the whole selection; a name taken at the last moment is defended by placing a file with a hard link, which fails if the name is there, and a folder with `create_dir`; `move_without_replacing` does the same for renames). A folder can't go into itself or below (canonical paths, so not through a link either); a move into the folder an item is in does nothing; names must be one plain component. A move inside one volume is a rename (same inode; instant whatever the size). A copy is `std::fs::copy` (on APFS a clone: 600 MB in about 100 µs, extended attributes and dates kept) into a hidden part file put in place without replacing; links are copied as links and never followed; sockets and pipes are left out. **What the pane does and what the queue does**: `local::Service::paste` (the pane's `MacFiles::paste`) does renames and copies up to `INLINE_BYTES` (256 MiB) and `INLINE_FILES` (5,000) on the spot, and otherwise answers `Unsupported` with nothing changed; the pane turns that into `Message::PasteViaMac`, and `app.rs` queues `Job::OnMac` (`queue_on_mac`), which runs `paste_queued` with progress (a file at a time: one huge file on a volume that can't clone shows no progress inside it) and Cancel (between files). A move to another volume is a copy, and each original goes to the Trash only once all of it is at the target at the size it had and nothing in it was left out (`Why::NotCopied`); failures and kept originals are `left`, which Retry moves. Tests force the other-volume path with `Service::copy_moves` (test-only); the Trash in tests is always a recorder. `TransferSummary::direction` is `Direction::Local` for these (titles say Copying/Copied, "Show in Finder" works), and the pane's banner says "Copying…" without "on the phone" (`shows_in_finder`).
- Copy and move through the Mac (`transfer/through_mac.rs` and `relay.rs`, for phones without CopyObject/MoveObject): `explorer::Service::check_paste` first makes the same checks the native paste does (nothing to do, a folder into itself, a read-only target). **One file at a time**: MTP cannot stream phone → phone, because a write holds the phone's one session until the whole file is in, so a read started from inside the write's data never returns (tried: it times out). So `download_run_onward` plans the tree once, reads each file into a private (`0700`) scratch folder (`tempfile`, removed on every exit), hands it to an `Onward` (`Relay`: it makes each phone folder when the walk reaches it, keeps the handles it made so files go into *its* folder and never one that merely has the same name, and sends the file with `Sender::send_file`), and deletes the scratch file whatever happened. The Mac therefore needs room for the biggest file, not for the selection (`the_mac_holds_one_file_at_a_time_not_the_selection`). A failure of the onward stage is that file's failure (`failed_folders` skips what is inside a folder that could not be made), and `Failure::stops_the_batch` decides as ever. Each selected item is named once on the phone, as Finder's "keep both" would (`free_name` only if the name is taken: it always returns a numbered name), so nothing is overwritten. The two halves report as one: `Meter::fold_in` rewrites each report so the totals are the selection's and `bytes_done` is half of what has been read plus half of what has been sent (the speed and time left are then the selection's). A copy never skips "the very file the phone already has", or copying a file into its own folder would do nothing; a move does (`Onward::has`, top-level files only, checked before the read), which is what lets a retry finish. A move reads every sent file back (`Sender` `verify`, `upload::judge`: the phone's size must equal the size sent; no size, or no answer about that object, is `unconfirmed`), and an item's originals go (`remove_originals`, same rules as a move to the Mac) only if every step of it was verified going down and `Relay::delivered` says confirmed going up; otherwise the whole item stays (`left`), with one `Why::Unchecked` note unless failures already say why. Retry of a move runs with `left` as its names and `resuming` (`Job::OnPhone(request, true)`, set by `Finished::retry_job` for a move that got part way, unless the first try numbered a folder because its name was taken (`SummaryResponse::renamed`: then a folder of that name is not the one it started), or failed outright (nothing is known of what it did, so the folder of that name is taken to be its own); never for a copy, and `resuming && moving` is checked again in the service): the `Relay` then merges a selected folder into the folder of the same name on the phone (`Placed::merge_into`, found in `Children`, which holds each pre-existing phone folder's children by name and the names this run has taken in it; each merged folder is read once, and the folders this copy made need no entry) instead of making `name (1)` beside it, and does so at every level. A file there already as it is (same size and date: the very file, or the numbered copy an earlier retry made, `Children::copy_of`) is neither read nor sent (`Onward::has`, which now looks in the folder the file would go into); a different file of the same name, or a file where a folder is, gets a numbered name beside it. Nothing on the phone is replaced. `TransferSummary::merged` counts selected folders merged into. **Files are not forced to the disk** on the way (`Copy::durable`): the scratch copy is deleted at once and the phone's copy is the one that counts; the same rule is off for a plain phone → Mac copy (the original stays on the phone; a per-file `fsync` cost 4.4 ms, 20 s for 5,000 photos) and on for a phone → Mac move, whose original is about to go, **including a file the move finds already in place** (`force_to_disk`: a plain copy may have written it unsynced); `SYNCS` counts it in tests. A relayed file's part is never kept for a later try (`Copy::resumable()`), so scratch holds one file. Read-back is only as good as the phone's answer: a phone that echoes the declared size would pass it.
- Drag onto a folder (phone pane; `Drag` in `handler/explorer/handler.rs`): `Request::Select` (a press on a row's name and glyph, or on a tile) arms it where `Volume::pastes_within`; `PointerLeft(pressed row)` makes it active; `PointerEntered` tracks the row under the pointer; the drop happens on `PointerReleased`, which `app.rs` sends from one window-level listener (`pointer_released`, any widget, any capture status) and not from rows, so no drop depends on event order between widgets. The drag's hint goes in the footer, never above the list: anything that appears above the rows when a drag starts slides them under a still pointer (test `starting_a_drag_moves_no_row_under_the_pointer`). `drag.over` is cleared by `forget_pointer` wherever rows can change without the pointer moving (scroll, entries, sort, view), and rows send `on_move` while `Dragging`, because iced keys a widget's hover state by tree position. Rows only get `on_enter`/`on_exit` while a button is down (`Pointer::Armed`/`Dragging` in `pressable`), so moving over a list publishes nothing; keep it that way, a message per row crossing would rebuild the view each time. A press on one of several selected rows defers narrowing to the release (`narrow_on_release`), but only where a drag can follow; a pane without drags must narrow at once, or nothing will. Escape cancels only a drag that has started (a stale press must not eat the Escape that clears the selection). `paste_into(mode, from, into)` is the one paste: the keyboard pastes into the folder shown, a drop into a subfolder, and `Pasted`/`PasteViaMac` carry that destination. The release is told to both panes (`Message::PointerReleased`); a drop is made by the pane the drag started in. **Spring-loaded folders**: a drag (the pane's own or `incoming`) held over a folder row starts `spring` (name, since); `App` subscribes to `SPRING_BEAT` (100 ms) only while `spring_pending()`, and after `SPRING_DELAY` (800 ms) `spring_into` goes there keeping the drag (`go` clears it), remembering `spring_origin`; Space during a drag is `spring_now` (`App::spring_held`), never Quick Look. `go` clears the selection, so a drag carries `Drag::source` from its start, and drops and `drop_across` use `dragged()`, never `selection()`. The list's `on_hover` is armed during the pane's own drag as well (`Drag::inside`): let go inside a sprung folder (no folder row under it) drops into the folder shown. Escape, a release with no target, or an incoming drag ending other than by a drop over this pane (`set_incoming(None, dropped)`, `dropped` = the message was `PointerReleased`) `spring_back` to the origin; `open`/`close` forget it. A test that moves the pointer in `iced_test` must send a `CursorMoved` event after `point_at`; `point_at` alone changes nothing a widget sees.
- Drop onto the sidebar (`handler/drop_spot.rs`): a sidebar entry is a `Spot` (`Mac(path)` or `Phone { storage_id, path }`; `places::Target` is the same type), and while a pane drags (`App::sidebar_drop`: `Origin` from `explorer::Handler::dragged_from`, read per redraw, so it copies the folder, never the names) the places handler's places and pins and the device handler's storages (`/`) and usual places are drawn through `drop_spot`, a `mouse_area` around a `stack` whose top layer is the outline (a border on the entry's own container is painted over by its button), so lighting it moves nothing; with no drag the entry is as it was, so moving over the sidebar publishes nothing. `SidebarDrop::accepts`: from the Mac anywhere, from the phone the Mac or its own storage (never another storage, nor the folder the items are in); a read-only storage takes nothing. `hover(spot, over)` names the spot, so the leaving of one heard after the coming onto the next can't undo it (`App::sidebar_hover`); `sidebar_over` is forgotten whenever no pane drags. On `PointerReleased`, `drop_on_sidebar` goes before `drop_across`: Mac → Mac `local_pane.paste_into`, Mac → phone `upload_to` (any storage of the open phone), phone → Mac `download_into`, phone → its storage `device_pane.paste_into`; the mode is `SidebarDrop::mode`, Finder's rule (same disk, by `mac_disk`: `/Volumes/<name>` or the start-up disk, or same storage → move, ⌥ copies; elsewhere → copy, ⌘ moves). Held `SPRING_DELAY` (the `SPRING_BEAT` subscription runs while `sidebar_spring_pending`), or Space, `spring_sidebar` opens the spot once in its pane through `explorer::Handler::spring_to(path)` (the pane's own drag goes on, an incoming one can then be dropped there; a release anywhere else `spring_back`s), a phone spot only on the storage the pane shows. The footer row clips, so a long drag hint stops at its pane's edge.
- Lasso and drops across panes (`handler/explorer/lasso.rs`, a wrapper outside the `scrollable` like `right_click`): it never captures; it publishes `PressedAt { at, size, taken }` for every left press (list-relative, `taken` = a child handled it), `LassoMoved` on every move while a lasso runs (even outside, for autoscroll), `Hover(bool)` on changes while a drag comes in, and draws the box. A press is told apart by **message order**: a row's name sends `Select` (may drag), the rest of the row `PressRow`, then the wrapper's `PressedAt` reads `pending_press` (reset by any other request at the top of `handle`): Name → nothing, Row → lasso, nothing and not taken → lasso in empty space (clears), nothing but taken → the scrollbar. The lasso anchors in content coordinates (`at.y + viewport.0`) and selects with the pure `window::rows_between` / `grid::tiles_touched` and `selection::swept` (plain replaces, ⌘ toggles, ⇧ adds; one pass, ~120 µs over 5,000 rows); it is re-applied on `Scrolled` and on `LassoTick`, which `app.rs` subscribes to (16 ms) only while `lasso_step()` is `Some` (past an edge, with room to scroll, and never before the list has a size). A drag across panes: `App::update` runs `sync_drags` after every message (`set_incoming(other.dragging())` only onto a pane that is shown, `set_other_pane`); an incoming drag makes rows report like a drag of its own (`Pointer::Dragging`), and `drop_into()` is the folder row under the pointer or the folder shown. `Message::PointerReleased` resolves `drop_across` **before** the panes hear the release (download/upload into that folder; ⌘ held = move, as Finder between disks), and `is_interaction` ignores rows crossing so Escape stays with the dragging pane.
- Big files and space: sizes, offsets and totals are `u64` end to end (MTP's own fields are 32-bit and `0xFFFFFFFF` means "4 GB or more"; `size_limit` treats it as unknown). Test with sparse files (`File::set_len`), which cost no disk, and resume from a sparse part rather than moving gigabytes. The sidebar's storage bars are refreshed by `device::Handler::reload_storages`, which `app.rs` calls after every finished transfer and every successful phone-side edit; do the same for any new feature that changes what is on the phone.
- A silent phone: mtp-rs documents that a wedged Pixel hangs with no error at all, so every wait on the phone has a limit and ends as `Timeout`. **"Silent" means nothing on the session made progress for the limit, not that one request waited that long**: the phone has one session, so requests queue, and a listing asked for behind a 3 GB upload would otherwise be called silent after a minute. `device::Service::activity()` is the shared clock (`device/activity.rs`): whoever hears from the phone calls `heard()` (every answered request, every chunk or window of a transfer: `Copy::advance`, the upload's progress callback), and a long request in flight counts as working until its own limit is up (`working`). The transfers' own waits are `phone_answers(activity, limit, work)` (90 s without progress, on the same shared clock: a request queued behind a long explorer request or another transfer's chunks is waited for; the upload's chunks say `heard()`, so `unless_stalled` is gone); every other request to the phone, in the explorer and around a transfer (planning, merging a folder, removing originals), uses `Limits` (`explorer/bounded.rs`, tied to the device's `Activity` by `Service::new` of the explorer and of the transfers; `Limits::default()` exists only in tests, so a request can't be made on a clock of its own; every wait goes through `Activity::within`): `limits.ask(request)` for one answered at once (60 s), `limits.long(request)` for one that works for minutes without a word (copying a folder, deleting one with its contents, a move to another storage: 10 min), `limits.scaled(is_folder, request)` for one whose work grows with what it touches (renaming or moving a folder rewrites the path of everything inside it), `read_children`/`read_all`/`limits.next` for a folder, whose limit is per item, never for the whole folder (20,000 files are 20,000 quick requests). A new request to the phone in the explorer without one is a bug that `every_request_in_the_explorer_has_a_limit` (it reads the source) fails on; the two raw seams, `Objects` and `Pasting`, live in `explorer/raw.rs` and are bounded by their callers (`delete_object`, `place_one`, which take `&Limits`). Test silence with `testing::silence` (a transfer that never gets its data holds the one session, so every request behind it waits: a real silent phone, which the virtual one can't otherwise be) and a busy phone with `testing::busy` (a trickling upload that reports each chunk: waited for, never given up on); or use a fake that never answers one call. The virtual phone answers within one poll, so a zero limit proves nothing. The device's own requests go through `device::Service::ask(epoch, request)` (silence is `Timeout` and drops that session) or `within(work)`: the storage list, the battery, every thumbnail request (`ThumbnailLost` tells the app a phone went silent mid-grid, so Reconnect is offered at once), and in `connect_to` both closing the old phone and opening the new one (`opening`): the slot lock is held while a phone opens, so an unbounded open would freeze everything that needs the phone. Opening can't be silenced on the virtual phone, so it is tested on `opening` with a future that never finishes; a mutation sweep that removes such a bound hangs that test instead of failing it (kill the test binary: a hang is a catch). `device::Service::handle_error` drops the session on `Timeout` as well as `Disconnected`, and `ErrorResponse::device_lost` is true for both so the device panel offers Reconnect. The virtual phone can only simulate a reset (`force_operation_wedge`), so test the silent case on the helpers. Progress reaches the UI as a stream (`iced::stream::channel` → `Task::run`); `app.rs` builds the request from the device pane's selection and the Mac pane's folder.
- Every file the app writes from a phone (downloads, imports, mirrors, the preview cache) is marked `com.apple.quarantine` before it is placed (`service/quarantine.rs`, one `setxattr` per file; with `local/dock.rs`, `local/awake.rs`, `local/menubar.rs`, `local/share.rs`, `local/screens.rs`, `doctor/system.rs` (`getuid`), `transfer/room.rs` and `places/mounts.rs` the only `unsafe` in the code), so the Mac checks it before it runs whoever opens it; a disk that can't hold the mark (FAT) still gets the file. Never place a phone file without it.
- The device is untrusted input. Before anything is written, transfer planning checks every device name with `names::is_safe_component` (one normal component: no `/`, NUL, `.`, `..`; a `\` is a legal Mac name and is allowed), keeps every target inside the destination, skips folders already visited (cycles) and caps depth (64) and items (1M). Files are placed with a hard link (atomic no-overwrite) and fall back to check-then-rename on file systems without links. A file may not send more than the size the phone reported (`check_within_size`, before the extra bytes are written; `0xFFFFFFFF` means "4 GB or more" and limits nothing), and a cancel is honoured unless the file has arrived in exactly its reported size (`cancel_stops`), so a phone can neither stream for ever nor use its own size to dodge a cancel.
- Search (`service/explorer/search.rs` `Walk`, `handler/search`, ⇧⌘F): the storage is walked once (depth-first, pieces of 500 items or 120 ms) into a catalogue the handler filters in memory per keystroke (`dto::SearchQuery`: every word in the name; a `FileKind` never matches a folder); never ask the phone per keystroke. Folders read in full go into the search index: `listings` is a `Remembering` (12 recent folders, plus an index of up to 20,000 folders / 200,000 items) whose `recall` checks both, `keep` refreshes the index only for folders it already holds, and `amend`/`forget_below` apply to both, so the index stays true through the app's own edits. Android's root folder count is the whole storage's count, so any change re-reads the root. A re-keyed folder lists as empty instead of failing: the walk asks an empty folder's object info, and on `StaleHandle`/`NotFound` restarts once (`restart: true`) after forgetting the storage's index. Hidden folders are walked only when hidden files are shown (`worth_walking`); a folder is entered once (`goes_into`). The search panel takes the phone pane's place; while open on the phone side, Escape closes it, ⌘A selects every result and other pane keys are ignored. Name, Size and Modified head columns the results can be ordered by (`order`, `mapper::next_order`: Size and Modified start largest/newest first, a second click turns round; sizes order as they read, MTP's 0xFFFFFFFF as 4.3 GB); ordered with nothing typed and no kind, the results are every file on the storage (`wanted`): what fills the phone. Names are lower-cased once per catalogue item (`lower`); pieces that arrive while ordered are ordered among themselves and merged in, one pass, keys moved beside their results, never all re-sorted (200,000 items in 400 pieces: 0.53 s in all on a release build). A header click clears the selection, as a new query does. Download makes one `download_as(Copy)` per folder into the Mac pane's folder; Show in folder uses `explorer::Handler::show_item` (navigate, then select once `Listed`). `close_device_pane` closes it.
- `explorer::Service::list` returns device order; ordering is the pure `explorer::sort`, which the handler re-applies on header clicks without another device round trip. Every header sorts, Kind too (`SortKey::Kind`, file value `kind`, starting A→Z like Name): folders, then the search's `FileKind`s in their order, other extensions, files without one, each grouped by lower-case extension (what the Kind column shows) and then by natural name; each entry's kind is worked out once per sort (it runs on the UI thread as a folder arrives), never per comparison.
- Filter (⌘F, either pane; whole-phone search is ⇧⌘F): a fixed-width field always in the pane's path row in a pane at least `layout::FILTERS_INLINE` (720) wide, and in a row of its own under the path in a narrower one (`filters_inline`; nothing moves when it is used), with a date menu (`filter_date`, a `pick_list` of `DateChoice`: Any date or a `dto::DateRange`, words from `format::date_label`, shared with the search; `format::date_span(range, today)` turns it into a `dto::DaySpan` of days, both ends included, counted back from the Mac's today (`format::local_today`, the handler's `today` fn so tests fix the day) and compared with the day the pane shows, `Timestamp::day`; a date leaves folders and undated files out) and a kind menu beside it (`filter_kind`, a `pick_list` of `KindChoice`: All kinds or a `FileKind`, words from `format::kind_label`, shared with the search; it shares the row by portion, at most `KIND_WIDTH`, and a picked kind never matches a folder); words, date and kind are one `SearchQuery` and are cleared together (the phone search has the same date menu, `search::Request::Date`); `rows` is the display form of what the filter leaves of `entries` (`shown` maps each row to its entry, `all_rows` is built once per listing so a keystroke only picks rows), every word in the name in any case (`dto::SearchQuery`, empty = everything). What it hides leaves the selection, so Delete, copy and drag act only on what is on screen; thumbnails go by `shown`. Escape clears the filter before the selection (from inside the field it takes two: iced's text field keeps the first, to let go of the cursor, but not ↑/↓, which move through what is shown); going to another folder clears it, a new reading of the same folder keeps it; Return in it opens a single match or picks the first.
- Android's app folders: Android 11 and later keep `Android/data` and `Android/obb` from computers, so on an Android phone (`Device::android` → `DeviceResponse::android` → `device::Handler::is_android`, which `app.rs` puts in the phone `Volume::hides_app_folders` when a storage opens) a pane at or inside one (`explorer::mapper::in_app_folders`, by path alone, any case, no request) that is empty says "Nothing here can be seen from a Mac" with `APP_FOLDERS_NOTE` instead of "This folder is empty", and a refused read there says `APP_FOLDERS_REFUSED` with the note in place of the error's own title and advice (which would send the user unplugging a phone that is fine); a lost phone (`device_lost`) is still said as one.
- Long names (`handler/explorer/middle_text.rs`): a row's or a tile's name is a `MiddleText`, cut in the middle to the room it is laid out in ("IMG_2026…2133.jpg": `middle_cut` keeps the start, a couple of letters at least, and the end with an extension of up to 8 characters, by character so Thai cuts cleanly), measured with the renderer's own paragraph in `layout` (a binary search over how many characters are kept) and kept per widget until the name or the room changes, so only rows on screen pay (3 ms for a screen of long names, 1,000 or 5,000 files, release). It reports the whole name to `operate`, so `iced_test`'s `find` still finds a row by its name. A name that probably doesn't fit (`probably_cut`, an estimate from its length and the room `name_room` works out from `Fit`) gets a tooltip with the whole name. Tiles keep one line.
- Row size (`dto::Density`, Settings "Rows"; `Settings::list_density`, file key `listDensity`, unknown = Standard): the pane's list rows come from `row_style(density)` (`RowStyle`: height 22/28/36, text sizes, glyph square), so `window::rows`, the spacers and `scroll_to_cursor` all use `row_height()`; never a fixed row height again. `set_density` scales `viewport.0` so the top row stays, only in List view. In `list_rows` the shading is `striped(absolute index)` (never the index within the built window) and `joined(index, look)` squares the corners a selected row shares with a selected neighbour. `row_fill` is target > selected > stripe; `row_text` lets text on a fill inherit its colour (an explicit `text::secondary` there is grey on blue). The folder/page `glyph` is drawn from containers (no svg feature), always in one square so names line up; a file's page has a band across its foot in its kind's colour (`EntryResponse::badge`, `mapper::badge`: the search's `FileKind` by extension, with .apk/.apks/.xapk as `BadgeKind::App`, not an archive; no band for a file of no known kind), and a tile with no thumbnail shows the badge (the extension, cut to 4 letters, on the kind's colour, the kind's word under it; a folder tile draws a large folder glyph). The badge is worked out once per listing, in the response mapper, never per redraw. `iced_test`'s `find` can't see a radio's label (the radio draws it): the settings test clicks by position from the "Rows" text.
- Groups (View › Use Groups, ⌃⌘0, `Shortcut::UseGroups`, Finder's own key, on by date or off; View › Group by Date / Kind / Size, `menubar::Command::GroupBy`, ticked by `State::group_by`; per pane in the settings, `Settings::mac_group`/`phone_group` as `dto::GroupBy`, file keys `macGroup`/`phoneGroup` ("none", "date", "kind", "size"; anything else none); `App::set_group`, `apply_settings` → `explorer::Handler::set_group_by`): the pure `handler/explorer/groups.rs` says each row's group (`bucket`: Date is Finder's Later, Today, Yesterday, Previous 7 Days, Previous 30 Days, each month of this year "September 2026", each earlier year "2025", No Date last, by `Timestamp::day` against the pane's `today`; Kind is Folders, Photos, Videos, Music, Documents, Archives, Other; Size is Folders, then "1 GB or More" (MTP's "4 GB or more" too) down to "Empty"), and `apply_filter` puts the shown rows in group order once per listing, sort or filter change (`arrange`: a stable sort, so the pane's own order holds inside a group) and keeps `groups` (start, len, bytes). Ungrouped, every old path runs as before (`groups` empty). Grouped, the list's lines are the rows plus a header a group, a row's height (`list_line`, `list_line_of`, binary search over groups); the grid starts each group on a new line under a `GRID_HEADER` (32 pt) header (`GridFrame`: `top(line)`, `line_at(y)`, `window`, `total`, O(log groups) a call), so `content_height`, the lasso (`grouped_touched`: headers left out, the grid's columns kept), `scroll_to_cursor` (by the line's place) and `visible_tiles` (thumbnails) cost what is on screen. A header (`group_header`, its label and `Group::summary` "2 items, 6.4 MB") is a button: `Request::SelectGroup(g)` selects the group, ⇧ adds it, ⌘ toggles it (all of it goes if all was selected). Arrows move over rows, so they cross headers; a header parts the rounded block of selected rows (`joined`). 5,000 files grouped build only what is on screen; regrouping 5,000 takes well under 500 ms (debug).
- Folder sizes (View › Calculate Folder Sizes, per pane: `Settings::mac_folder_sizes`/`phone_folder_sizes`, `menubar::Command::ToggleFolderSizes`, ticked by `State::folder_sizes`; `explorer::Handler::set_folder_sizes`): after a listing, and only in List view, each folder shown is counted in turn (`count_sizes`/`next_size`, one at a time: the phone has one session) through `Service::folder_size` (the phone's `tally`, bounded and reusing the folder memory; the Mac's `tally` off the UI thread), its cell saying "Counting…" and then the bytes (`mapper::folder_size`, "+" when some couldn't be counted). Sizes live beside the entries (`sizes`), never in `size_bytes`, so the status line still sums files; a cell is patched in place (`show_size`), and only a Size ordering re-sorts (stable, folders as their contents). Another folder, a fresh reading (`load(false)`) or turning it off forgets them; Grid or a change of folder stops the count (`size_run` drops a late answer); a lost phone ends it.
- Tile size (View › Make Tiles Bigger / Smaller, ⌘= or ⇧⌘= and ⌘−; `Shortcut::TilesBigger`/`TilesSmaller`, `App::step_tiles`, only for a pane in Grid view; greyed at the limits through `menubar::State::tiles_biggest`/`tiles_smallest`): `dto::TileSize`, one of `STEPS` (96, 112, 132, 160, 192 points; 132 is the usual), per pane in the settings (`Settings::mac_tiles`/`phone_tiles`, file keys `macTiles`/`phoneTiles` in points, anything not a step read back as the usual). The grid's geometry is `grid::Tile` (width, `height()` = width + 18, `row_height()`, `pitch()`), passed to `grid::columns`, `visible` and `tiles_touched`; `explorer::Handler::set_tile_size` keeps the first tile in view and asks thumbnails for what came into it. Thumbnails are made at the biggest step (`THUMBNAIL_SIZE` = 192), so they are only ever shrunk; the disk cache's `MAGIC` moved to `OMCTHMB2`, so one made at 160 is a miss and made again.
- Narrow panes and column widths: `handler/explorer/layout.rs` decides which optional columns fit a pane's width (`for_width(width, ColumnWidths)`: Kind steps aside first, then Size, whenever Name would get narrower than `NAME_LEAST`; Modified is squeezed, never dropped); the pane is wrapped in `responsive`, so it needs no window-size state. Kind, Size and Modified are as wide as the user made them (`dto::ColumnWidths` in points, `Settings::mac_columns`/`phone_columns`, file keys `macColumns`/`phoneColumns`, written only once changed, read back within `LEAST`..`MOST`); Name takes the rest. The gap left of a column in the header is its handle (`Request::ResizeColumn(edge, width)`, carrying the list's laid-out width from `Fit`, since the scroll viewport's width is only known after a scroll; a double-click is `ResetColumns`); while a resize runs `App` subscribes to pointer movements (`resize_pointer` → `ColumnResize` → `explorer::Message::ResizeMoved`), never otherwise, and the pure `layout::resized` moves the edge: the column right of it grows as it moves left, the one left of it gives the room (Name, down to its least, when it is Name). The release saves the widths if they changed. Header cells and row cells use the same fixed widths and gap, so they line up.
- Mac thumbnails for HEIC/video/DNG/PDF come from Quick Look (`qlmanage -t`). It can hang on odd files, so it always runs with a timeout, `kill_on_drop`, a 2-permit semaphore and an existence check first.
- `mtp-rs` warns that cancelling an in-flight read can wedge Android devices; wrap long operations in a timeout and prefer `download_windowed`.
